# Diary — Single-user MVP specification

## Goal

Build a local web application in which one user can create, browse, read, edit, and delete private diary entries. The MVP should provide a complete and reliable diary workflow without authentication or multi-user functionality.

## Scope

The MVP includes:

- creating a diary entry
- listing saved entries in reverse chronological order
- opening and reading an individual entry
- editing an existing entry
- deleting an entry after explicit confirmation
- persisting entries between application restarts
- clear empty, loading, validation, and error states
- a responsive and keyboard-usable interface

The MVP does not include:

- authentication, registration, passwords, sessions, or user accounts
- multiple users, entry ownership, sharing, or permissions
- cloud synchronization or collaboration
- rich-text or Markdown rendering
- attachments, images, comments, reminders, or notifications
- analytics containing diary content
- deployment to a public or otherwise untrusted network

## Diary entry

Each entry contains:

- `id`: a stable, globally unique identifier generated by the application
- `title`: required plain text
- `content`: required plain text
- `entryDate`: a calendar date in `YYYY-MM-DD` format, without a time or time zone
- `createdAt`: creation timestamp generated by the application
- `updatedAt`: most recent update timestamp generated by the application
- `tags`: an optional list of plain-text labels

Timestamps are stored as UTC ISO 8601 values. The UI formats dates and timestamps using the user's local time zone.

## Validation

- Trim surrounding whitespace from the title, content, and tags before saving.
- Reject an empty title.
- Reject empty content.
- Require a valid `entryDate`.
- Remove empty tags and duplicate tags using case-insensitive comparison.
- Limit the title to 200 characters, content to 50,000 characters, each tag to 50 characters, and the tag list to 20 tags. Enforce the limits in the validation layer and show understandable validation messages in the UI.
- Validate persisted or externally supplied data at the application trust boundary; do not rely only on form controls.
- Treat entry content as plain text and never render it as unprocessed HTML.

## User flows

### Browse entries

1. Opening the application displays the entry list.
2. Entries are ordered by `entryDate` descending, with `createdAt` descending as the tie-breaker.
3. Each list item shows at least the title and entry date.
4. Selecting an item opens the complete entry.
5. When no entries exist, the application shows an empty state with an action to create the first entry.

### Create an entry

1. The user opens the new-entry form.
2. The form accepts a title, content, entry date, and optional comma-separated tags.
3. The entry date defaults to the user's current local date.
4. Invalid input keeps the entered values visible and displays field-level feedback.
5. A successful save persists the entry, opens the saved entry, and provides clear success feedback.

### Edit an entry

1. The user opens an existing entry and chooses to edit it.
2. The edit form starts with the saved values.
3. Saving valid changes updates `updatedAt` but preserves `id` and `createdAt`.
4. Cancelling does not persist changes.
5. Attempting to edit a missing entry displays a not-found state without creating a replacement.

### Delete an entry

1. The user chooses to delete an existing entry.
2. The application asks for explicit confirmation and identifies the entry being deleted.
3. Cancelling leaves the entry unchanged.
4. Confirming permanently removes the entry and returns to the list with clear feedback.
5. Attempting to delete a missing entry displays an appropriate not-found response.

## Persistence and architecture

- Use durable local persistence; entries must remain available after restarting the application.
- Access persistence through a dedicated repository boundary rather than directly from UI components.
- Keep business rules in the application or domain layer so they can be tested without rendering the UI.
- Use database migrations for schema changes when the selected persistence technology requires a schema.
- Do not add a user table, `userId`, mock login, global current-user value, or authorization layer to the MVP.
- Keep repository and service interfaces extensible enough that an authenticated user context and entry ownership can be added in a later version without rewriting the core UI flows.
- Do not choose a specific framework, database, or ORM in this specification. Record those decisions once selected by updating project documentation.

## Privacy and operational constraints

- Treat all diary content as sensitive.
- Do not include diary titles, content, or tags in application logs, analytics, error reports, or thrown error messages.
- Use only fictional diary content in tests and fixtures.
- Do not expose the unauthenticated MVP directly to an untrusted network.
- Do not commit secrets, real diary data, or local database contents to version control.

## Accessibility and usability

- All primary actions must be usable with a keyboard.
- Form fields must have programmatically associated labels.
- Validation and operation errors must be presented as text and must not rely on color alone.
- Focus should move predictably after navigation, validation failure, and confirmation dialogs.
- Destructive actions must be visually and semantically distinguishable from ordinary actions.
- The main workflows must remain usable without horizontal page scrolling at viewport widths of 320 px and 1280 px.

## Test expectations

Automated tests must cover at least:

- creating and persisting a valid entry
- rejecting each invalid required field
- enforcing the specified maximum lengths
- normalizing tags
- listing entries in the specified order
- reading, editing, and deleting an existing entry
- preserving `id` and `createdAt` during edits
- handling missing entries for read, update, and delete operations
- cancelling edits and deletion
- ensuring diary content is treated as text rather than executable HTML

Tests must be deterministic. Control the clock and identifier generation where needed.

## Acceptance criteria

All acceptance criteria are required for the MVP.

### Core functionality

#### AC-01 — Empty diary

Given no diary entries have been saved<br>
When the user opens the application<br>
Then an empty state is displayed<br>
And the empty state includes an action for creating the first entry

#### AC-02 — Create an entry

Given the user is on the new-entry form<br>
When the user enters a valid title, content, and entry date<br>
And submits the form<br>
Then a new entry is persisted<br>
And the application displays the saved entry<br>
And the entry has an `id`, `createdAt`, and `updatedAt`

#### AC-03 — Required-field validation

Given the user is creating or editing an entry<br>
When the user submits an empty or whitespace-only title or content<br>
Then the entry is not persisted<br>
And field-level validation feedback is displayed<br>
And values entered in the other fields remain visible

#### AC-04 — Maximum lengths

Given the user is creating or editing an entry<br>
When the title exceeds 200 characters, content exceeds 50,000 characters, a tag exceeds 50 characters, or the entry contains more than 20 tags<br>
Then the entry is not persisted<br>
And the affected field displays an understandable validation message

#### AC-05 — Default entry date

Given the user opens the new-entry form<br>
When the form is displayed<br>
Then the entry date defaults to the user's current local date

#### AC-06 — List entries

Given multiple entries have been saved<br>
When the user opens the entry list<br>
Then entries are ordered by `entryDate` descending<br>
And entries with the same `entryDate` are ordered by `createdAt` descending<br>
And every list item displays at least its title and entry date

#### AC-07 — Read an entry

Given an entry exists<br>
When the user selects it from the entry list<br>
Then the complete title, content, entry date, and tags are displayed

#### AC-08 — Edit an entry

Given an entry exists<br>
When the user changes valid fields and saves the entry<br>
Then the changes are persisted<br>
And `updatedAt` is changed<br>
And `id` and `createdAt` remain unchanged

#### AC-09 — Cancel editing

Given the user has changed values in the edit form<br>
When the user cancels editing<br>
Then none of the unsaved changes are persisted

#### AC-10 — Request deletion

Given an entry exists<br>
When the user initiates deletion<br>
Then the application requests explicit confirmation<br>
And identifies the entry being deleted<br>
And the entry remains unchanged until deletion is confirmed

#### AC-11 — Confirm deletion

Given the deletion confirmation is displayed<br>
When the user confirms deletion<br>
Then the entry is removed from persistence<br>
And it no longer appears in the entry list<br>
And the application displays clear success feedback

#### AC-12 — Cancel deletion

Given the deletion confirmation is displayed<br>
When the user cancels deletion<br>
Then the entry remains persisted and unchanged

#### AC-13 — Missing entry

Given the requested entry does not exist<br>
When the user attempts to read, edit, or delete it<br>
Then a not-found state is displayed<br>
And no replacement entry is created<br>
And the application provides a way back to the entry list

#### AC-14 — Tag normalization

Given the user enters tags containing surrounding whitespace, empty values, or case-insensitive duplicates<br>
When the entry is saved<br>
Then surrounding whitespace is removed<br>
And empty tags are discarded<br>
And duplicate tags are stored only once

#### AC-15 — Loading feedback

Given an entry list or entry detail is being loaded, or an entry save or deletion is in progress<br>
When the operation has not completed<br>
Then the application displays clear loading feedback<br>
And it prevents duplicate save or deletion submissions

### Persistence and security

#### AC-16 — Persistence across restarts

Given at least one entry has been saved<br>
When the application is stopped and started again<br>
Then the saved entry remains available with the same data and identifier

#### AC-17 — Persistence failure

Given persistence is unavailable or an operation fails<br>
When the user attempts to save or delete an entry<br>
Then the application displays a non-sensitive error message<br>
And does not falsely report success<br>
And existing persisted data is not silently lost

#### AC-18 — Safe text rendering

Given an entry contains text that resembles HTML or JavaScript<br>
When the entry is displayed<br>
Then the content is shown as text<br>
And no embedded markup or script is executed

#### AC-19 — Sensitive-data logging

Given a diary entry is created, read, updated, or deleted<br>
When application logs and error messages are inspected<br>
Then they do not contain the entry title, content, or tags

### Quality criteria

#### AC-20 — Keyboard operation

Given the application is being used without a pointing device<br>
When the user navigates through each primary CRUD workflow<br>
Then all controls can be reached and activated using the keyboard<br>
And keyboard focus remains visible and moves predictably

#### AC-21 — Responsive layout

Given the application is opened at a viewport width of 320 px or 1280 px<br>
When the user completes each primary CRUD workflow<br>
Then all required content and controls remain usable<br>
And the page does not require horizontal scrolling

## Definition of done

The MVP is complete when:

1. All acceptance criteria above are satisfied.
2. Relevant automated tests pass.
3. TypeScript type checking, linting, and the production build pass when their scripts are available.
4. Setup instructions explain how to install dependencies, start the application, run checks, and locate local data.
5. The selected framework, persistence technology, and relevant architectural decisions are documented.

## Future work

Deferred product ideas are collected in `INBOX.md`. After the single-user MVP is stable, the project may add:

- user accounts and authentication
- ownership of diary entries and server-side authorization checks
- migration of existing entries to the initial user's account
- secure deployment and managed persistence
- search, filtering, and richer tag management
- export, backup, and restore

Future work is not part of the current MVP unless this specification is explicitly updated.
